# UI 文本可译性调查（2026-11-20，游戏进程 7092）

## 一、会话级覆盖率审计（可复现）
工具 `work/p5/t_audit_session.py`：读取 `cnpatch/msglog.bin` 里本会话显示过的全部原文，
逐条在 `cnpatch_txt.bin` 里做二分查找并检查长度。
结果：**176 条 / 命中 176 / 缺失 0 / 超长 0**。即本会话玩家看到的每一句都有译文且能原位放下。

## 二、右键菜单不是 Win32 菜单
右键（画面中央）后枚举窗口，**没有**出现新的顶层窗口（无 #32768 菜单窗口），说明游戏内右键菜单
是引擎自绘；同时说明「保存/读取界面」也不是独立对话框窗口，而是在游戏画面里绘制。

## 三、内存里的 SJIS UI 串（右键菜单打开/关闭两种状态对比，命中数完全相同）
| 字符串 | SJIS 命中 | 备注 |
| --- | --- | --- |
| 最初から | 64 | 多在 0x3fxxxxxx 堆区，疑为标题画面残留 |
| 続きから | 1 | 0x4395879 |
| セーブ | 30 | 含 MEM_IMAGE（0xb645a4 / 0x3189e58 …） |
| ロード | 24 | 含 MEM_IMAGE（0x40bf64 …） |
| バックログ | **0** | 菜单里明明有这一项 |
| テキスト自動送り / コンフィグ | **0** | |

→ **右键菜单的字不来自这些 SJIS 串**；把这 54 处 セーブ/ロード 全改成 `ZZZZZZ` 后重开菜单，
画面无任何变化（像素 diff 只命中底部消息区的常规噪声），已全部还原。

## 四、意外发现：rvmm.dll 里有 UTF-16 对话框模板
- `0x031BBA9E`（rvmm.dll 内，MEM_IMAGE）附近是一段 DLGTEMPLATE 风格的 UTF-16 串：
  `セーブデータ選択` / `ＭＳ Ｐゴシック` / `ロード` / `コメント編集(&C)` / `重要度(&P)` / `セーブファイル…`
- `0x100BD5F6`（Vm60.dll 数据段）附近：`セーブ中` / `ＭＳ Ｐゴシック` / `ただいまセーブ中です` / `しばらくお待ちください。` / `バージョン情報(relic U.G.P …`
- 这些是 MFC/资源对话框模板（U+FFXX 控制字节可见）。但游戏内保存/读取界面并未创建独立窗口，
  所以它们很可能是引擎遗留/工具用模板，**不是**当前读档界面的文字来源。

## 五、结论与后续可用路线
1. 标题菜单 / 右键菜单 / 读档卡片标签：目前证据指向「引擎自绘 + 非 SJIS 明文」，
   靠内存文本替换很难，需要逆绘制层或改资源。
2. 若要继续做 UI 汉化，优先级建议：
   a) 用 `GetCachedFont`（UnivUI 序数 472）钩子 + 栈回溯，先定位「整行渲染」函数（一次性投入，之后所有 UI 文字都能拦）；
   b) 或在对话框模板路径上做实验（需先确认哪个界面真的走 MFC 对话框）；
   c) 暂不改动已发布的 v1.19。

## 六、残留风险量化（2026-11-20 复核，重要）

`cnpatch.c` 的 `my_GetGlyphOutlineA`（IAT 钩子版）逻辑是：
```c
if (find_uni((unsigned short)ch, &uni)) { hit = 1; }        /* ch = 原始 SJIS 码，正确 */
else if (g_nrmap && find_rev(ch, &uni)) { hit = 2; }        /* ch = 原始 SJIS 码，但 g_rmap 用 Unicode 作键 → 语义错配 */
```
`build_rmap()` 的键是 `MultiByteToWideChar(932, 隧道码)` 得到的 Unicode，所以只要某个“原生字符”的
SJIS 码在数值上等于某个隧道码的 cp932 Unicode，就会被误画。

新表（`cnpatch_uni.bin`，3,091 条）静态复核结果：**仍有 384 条这样的配对**，例如
`tunnel E3FC -> 拽` 会吃掉 `゜(0x814B)`，`tunnel E446 -> 熊` 会吃掉 `〈(0x8171)`，
`tunnel E449 -> 砂` 会吃掉 `’(0x8166)`，`tunnel E44B -> “` 会吃掉 `＜(0x8183)`，
`tunnel E443 -> 疚` 会吃掉 `ヾ(0x8153)`。

- **为什么现在没出问题**：构建期 `_safe_code()` 已经保证「语料 + 名牌里出现过的字符」不会成为受害者，
  所以正文/名牌（玩家看到的 99% 文本）不会错；剩下的 384 个受害者只会出现在**非语料文本**（引擎 UI、菜单、DLC HUD）。
- **正确修法（建议 v1.20 做）**：A 路径不该用 Unicode 键，二选一：
  a) `build_rmap()` 改成以「原始两字节码」为键（同一套表同时服务 A 路径），W 路径另建 Unicode 键表；
  b) 或删掉 A 路径的 `find_rev` 回退（前提是确认没有「先转 Unicode 再调 A 版」的调用方，需 A/B 实测）。
  两者都需要重启游戏实测，故今晚未改动已发布的 v1.19。
